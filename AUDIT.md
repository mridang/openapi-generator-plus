# SDK Harmonisation Audit — Round (2026-06-02)

Produced by the `PROMPT.md` review (9 parallel dimension agents). This is a
**triage list only** — nothing is fixed in the audit pass. Each finding is
DIVERGENCE (the harmonisation target) or UNIFORM-GAP (all 12 share it — a
feature request, not a parity defect). WONTFIX items from `AGENT.md` were
excluded by every agent.

## Meta-theme: fail-loud vs fail-silent (the dominant cluster)

The single biggest pattern across dimensions is **some SDKs surface an error
the others swallow**. It recurs in transport (redirect refusals), OAuth
(token-fetch errors), non-OAuth auth (malformed credential), model serde
(oneOf no-match), and the error model (dropped transport cause). Two of these
are **fail-open security postures** (auth credential silently dropped → request
sent unauthenticated). Fixing the cluster to a single "fail closed, surface a
typed SDK error" rule harmonises ~8 findings at once.

### `form-array-field-wire-divergence` — 🟡 dormant (needs fixture)
*Value serde / form body (application/x-www-form-urlencoded)*

Array-valued form fields serialize to wholly different wire bytes (and Elixir crashes) because form bodies bypass the shared ValueSerializer/collectionFormat path

- **A — ruby, php**: Array form field emitted as repeated keys: x=1&x=2. Ruby uses URI.encode_www_form(body) (ruby/base_api.mustache:207) which expands arrays into repeated pairs; PHP buildQuery() iterates array members emitting one k=v per element (php/base_api.mustache buildQuery, is_array branch).
- **B — java, kotlin, csharp, go, node, python, dart, swift, rust, elixir**: No SDK on this side produces repeated keys, and each produces a DIFFERENT single value. Java String.valueOf(List) -> "[1, 2]" (java/base_api.mustache:209); Kotlin value.toString() -> "[1, 2]" (kotlin/base_api.mustache:176); C# kv.Value?.ToString() on a List -> the TYPE NAME "System.Collections.Generic.List`1[...]" (csharp/base_api.mustache:208); Go fmt.Sprintf("%v") -> "[1 2]" space-separated (go/base_api.mustache:239); Node URLSearchParams coerces array -> "1,2" comma-joined (node/base_api.mustache:310); Python urlencode(body) without doseq -> the Python list repr "%5B1%2C+2%5D" (python/base_api.mustache:201); Dart '${options.x}' -> "[1, 2]" (dart/api/api.mustache:251); Swift "\(options.x)" -> "[1, 2]" (swift/api/api.mustache:302); Rust object_serializer::stringify -> JSON "[1,2]" (rust/api/api.mustache:341); Elixir URI.encode_query(body) RAISES ArgumentError because it rejects list values (elixir/base_api.mustache:296, value put raw at elixir/api/api.mustache:271).
- **Caller impact**: A server receiving an x-www-form-urlencoded body with an array field sees a different request from every SDK: repeated keys (Ruby/PHP), comma-joined (Node), space/bracket-mangled literals (Java/Kotlin/Go/Dart/Swift/Python), a JSON array (Rust), a .NET type name (C#), or a hard crash before the request is even sent (Elixir). Only repeated-key form is RFC-conformant for arrays. Unlike query params, form fields never route through ValueSerializer.serializeStyled / collectionFormat, so the explode/csv contract is lost entirely.
- **Canonical**: Repeated-keys (Ruby/PHP) per OpenAPI form-style explode semantics. Route form-field values through the same ValueSerializer styled/collectionFormat machinery used for query params so all 12 emit identical bytes, and stop Elixir from crashing.
- **Evidence**: ruby/base_api.mustache:207 vs php/base_api.mustache(buildQuery is_array branch) | java/base_api.mustache:209 | kotlin/base_api.mustache:176 | csharp/base_api.mustache:208 | go/base_api.mustache:239 | node/base_api.mustache:310 | python/base_api.mustache:201 | dart/api/api.mustache:251 | swift/api/api.mustache:302 | rust/api/api.mustache:341 | elixir/base_api.mustache:296 + elixir/api/api.mustache:271

### `dart-charset-utf16-mojibake` — ✅ confirmed
*Unicode / charset / byte-level (response charset detection)*

Dart response decoder only recognises utf-8/latin1/ascii and silently misdecodes (or throws on) all other charsets including UTF-16, while the other 11 decode them correctly

- **A — csharp, elixir, go, java, kotlin, node, php, python, ruby, rust, swift**: All 11 honour a non-trivial set of response charsets and decode UTF-16 (and other non-latin1 charsets) correctly. Native-registry langs use Charset.forName / Encoding.GetEncoding / Charset.forName (java/default_api_client.mustache:343 parseCharset->Charset.forName; csharp/default_api_client.mustache GetEncodingFromContentType->Encoding.GetEncoding; kotlin/default_api_client.mustache:468 charsetFor->Charset.forName). Go has explicit utf-16/utf-16le/utf-16be branches with surrogate-pair handling (go/default_api_client.mustache:434-437, 448-486). Swift maps utf-16/utf-16be/utf-16le/utf-32/shift_jis/euc-jp/windows-125x (swift/default_api_client.mustache:354-371). Elixir maps utf-16/utf-16le/utf-16be (elixir/default_api_client.mustache:292-295). Rust uses encoding_rs::Encoding::for_label (rust/default_api_client.mustache:690). Node uses TextDecoder(cs) (node/default_api_client.mustache:444). Python data.decode(charset) (python/default_api_client.mustache:68-70). Ruby Encoding.find (ruby/default_api_client.mustache:299). PHP mb_convert_encoding (php/default_api_client.mustache:551).
- **B — dart**: Dart's _encodingFor switch only has cases for iso-8859-1/latin1/ascii/utf-8/utf8 and a `default: return utf8` (dart/default_api_client.mustache:482-501). A response declared `Content-Type: application/json; charset=utf-16` is classified as text (dart/default_api_client.mustache:339 _isTextContentType matches application/json), then the raw UTF-16 bytes are passed to `utf8.decode(responseBytes)` (line 340). dart:convert's utf8 decoder rejects malformed input by default (allowMalformed:false), so non-ASCII UTF-16 bodies raise an unhandled FormatException; pure-ASCII content interleaved with NUL bytes is mangled. The doc comment claims unknown charsets 'fall back to UTF-8 rather than throwing' (lines 478-480) but that promise is false for actual non-UTF-8 bytes.
- **Caller impact**: A server response with charset=utf-16 (or any charset outside utf-8/latin1/ascii, e.g. shift_jis, windows-1251, euc-jp) is either thrown as an uncaught FormatException or decoded to mojibake in Dart, while every other SDK returns correct text. This is the exact silent-mis-decode bug that was already fixed for Go (AGENT.md Gap AE, commit aeab1276) but Dart was never brought to parity. Caller observes a crash or corrupted response body / failed JSON parse where the same wire bytes succeed in all 11 sibling SDKs.
- **Canonical**: Bring Dart to parity with the other 11: add explicit utf-16/utf-16le/utf-16be branches (Dart core has no built-in UTF-16 codec, so decode via a small surrogate-aware routine like Go's decodeUtf16, honouring the BOM) and, at minimum, use allowMalformed:true on the UTF-8 fallback so an unrecognised charset cannot throw — matching the documented 'fall back, never break decoding' contract and the lenient (replace/lossy) behaviour of python/ruby/rust/node.
- **Evidence**: dart/default_api_client.mustache:482-501 (_encodingFor switch: only latin1/ascii/utf8, default->utf8) and dart/default_api_client.mustache:339-340 (utf8.decode of raw bytes) vs go/default_api_client.mustache:434-486 (utf-16 branch + decodeUtf16) and swift/default_api_client.mustache:354-371 (utf-16/utf-32/shift_jis/euc-jp/windows-125x) and java/default_api_client.mustache:343 (Charset.forName) and rust/default_api_client.mustache:690 (encoding_rs for_label)

### `multipart-field-name-ascii-fold-python` — 🟡 dormant (needs fixture)
*injection / multipart Content-Disposition field-name encoding*

Python ASCII-folds non-ASCII multipart field NAMES (café -> caf?); other 11 SDKs preserve the raw UTF-8 field name

- **A — python**: Every multipart part routes the field name through `_build_disposition(name, ...)` -> `_sanitize_multipart_filename(name)`, taking only the ASCII-fallback element and discarding the rfc5987 form. For a non-ASCII name, `filename.encode('ascii', errors='replace')` replaces each non-ASCII char with U+003F '?', so a field named `café` is emitted on the wire as `Content-Disposition: form-data; name="caf?"`. The field name is silently corrupted; no `name*` parameter is emitted (RFC 7578 expects raw UTF-8 in `name`).
- **B — csharp, dart, elixir, go, java, kotlin, node, php, ruby, rust, swift**: All 11 validate the field name (reject CR/LF/NUL) and then only backslash-escape `\` and `"`, interpolating the original UTF-8 bytes verbatim into `name="..."`. A field named `café` is emitted as `name="café"` (raw UTF-8), which servers parse correctly per RFC 7578.
- **Caller impact**: Wire-format / data-shape corruption: with the Python SDK a multipart upload whose form field name contains any non-ASCII character has that name mangled to `?` placeholders, so a server keying on the exact field name (e.g. `名前`, `café`) receives a different field name than every other SDK sends and fails to locate the field. Same call, same input -> different multipart bytes and different server-side routing depending on SDK.
- **Canonical**: The 11-SDK behaviour wins: validate CR/LF/NUL then backslash-escape only `\` and `"`, preserving the raw UTF-8 field name in `name="..."`. Python should stop routing the field NAME through the filename ASCII-fallback path (that path is correct for `filename=` where an ASCII fallback plus `filename*` is the RFC 5987 idiom, but field names have no `name*` mechanism and must carry raw UTF-8). Give Python a dedicated `escape_multipart_field_name` that mirrors the other SDKs.
- **Evidence**: python: src/main/resources/templates/python/default_api_client.mustache:689 (`safe_name, _ = _sanitize_multipart_filename(name)`) + :95-96 (`ascii_fallback = filename.encode('ascii', errors='replace')...`) + :690 (`disposition = f'form-data; name="{safe_name}"'`). node: src/main/resources/templates/node/default_api_client.mustache:386-389 (`escapedName = name.replace(/\\/g,...).replace(/"/g,...)` — raw UTF-8 preserved). java: src/main/resources/templates/java/default_api_client.mustache escapeMultipartFieldName (`fieldName.replace("\\",...).replace("\"",...)`). go: src/main/resources/templates/go/base_api.mustache:283 `writer.WriteField(name, v)` + :388 escapeQuotes (no ASCII fold). dart: dart/default_api_client.mustache:574 escapeMultipartFieldName. rust: rust/base_api.mustache:412-414. swift: swift/base_api.mustache sanitizeQuotedHeaderValue. php: php/default_api_client.mustache validateMultipartFieldName (+ Symfony escape). ruby: ruby/default_api_client.mustache sanitize_multipart_field_name. elixir: elixir/default_api_client.mustache sanitize_multipart_field_name.

### `node-hardcoded-redirect-strip-list` — ✅ confirmed
*HTTP transport / redirect security boundary (SSRF & credential leakage)*

Node strips a hardcoded fixed set of provider API-key headers on cross-origin redirect instead of the spec-declared apiKey-in-header names like the other 11 SDKs

- **A — node**: SENSITIVE_HEADER_NAMES is a purely static, hardcoded Set that lists authorization, cookie, proxy-authorization plus a fixed list of common SaaS provider key headers (x-api-key, api-key, apikey, x-auth-token, auth-token, x-access-token, access-token, x-functions-key, x-amz-security-token, ocp-apim-subscription-key, fastly-key, cf-access-client-id, cf-access-client-secret). The template never interpolates the codegen-provided {{#apiKeyHeaderNames}} list, so the set is completely independent of the actual OpenAPI security schemes.
- **B — csharp, dart, elixir, go, java, kotlin, php, python, ruby, rust, swift**: All 11 strip authorization, cookie, proxy-authorization PLUS exactly the apiKey-in-header header names harvested from the spec's securitySchemes (apiKey/in:header) via the shared {{#apiKeyHeaderNames}} codegen list, so the stripped set matches the credential headers the SDK actually attaches.
- **Caller impact**: Security boundary diverges in both directions. (1) Under-strip / credential leak: if the spec declares an apiKey-in-header scheme whose name is NOT in Node's hardcoded list (e.g. X-Tenant-Key, X-Subscription-Id), Node forwards that API key across a cross-origin 3xx redirect to an attacker-controlled host, leaking the credential; the other 11 strip it. (2) Over-strip / dropped header: Node strips ~13 fixed names that may not be credentials in a given spec (e.g. access-token, auth-token), so a legitimate non-sensitive header matching one of those names is silently dropped on a cross-origin redirect in Node only, while the other 11 forward it. Same spec, two different request byte streams after a redirect.
- **Canonical**: The 11-SDK behaviour wins: derive the stripped header set from the spec via {{#apiKeyHeaderNames}} (in addition to the static authorization/cookie/proxy-authorization triple). Node should interpolate apiKeyHeaderNames into SENSITIVE_HEADER_NAMES and drop the hardcoded provider list so the credential-stripping boundary is spec-accurate and uniform across all 12 SDKs.
- **Evidence**: side A (node): src/main/resources/templates/node/default_api_client.mustache:38-56 (static Set, no {{#apiKeyHeaderNames}}) and :275 (crossOrigin strip uses SENSITIVE_HEADER_NAMES); grep confirms apiKeyHeaderNames is never referenced in node/default_api_client.mustache. side B: java/default_api_client.mustache:215-224; go/default_api_client.mustache:327-334; csharp/default_api_client.mustache:47-56; dart/default_api_client.mustache:234-244; kotlin/default_api_client.mustache:38-43; php/default_api_client.mustache:39-46; python/default_api_client.mustache:366-375; ruby/default_api_client.mustache:49 + :186-187; rust/default_api_client.mustache:26-30; swift/default_api_client.mustache:632-636; elixir/default_api_client.mustache:410-416. Codegen source populating apiKeyHeaderNames from apiKey/in:header schemes: src/main/java/io/github/mridang/codegen/generators/AbstractBetterCodegen.java:538-552,659-666.

### `authenticator-secret-in-default-string-repr` — ✅ confirmed
*Non-OAuth authenticators / credential exposure*

Bearer/Basic/ApiKey authenticators leak the stored token, password, api-key (and client_secret) through the language's default object string representation in 5 SDKs but not the other 7

- **A — python, ruby, elixir, node, go**: The secret is stored in a field that the language's default/idiomatic stringification dumps verbatim. Python: BearerAuthenticator/BasicAuthenticator/ApiKeyAuthenticator are `@dataclass(frozen=True)` whose auto-generated `__repr__`/`__str__` print every field, so `repr(auth)`, an f-string, or `logging ... %r` emits `BearerAuthenticator(host='...', token='SECRET')`.
