# Trace context from the caller's context: audit of the other eleven SDKs (issue #136, item of #131)

Status: proposal for owner review. Nothing here is built, and no existing file is changed by this document. It records what the audit of the eleven non-Go SDKs found and fixes one set of promises, tests and docs for all twelve.

Evidence marks used below: "verified in <file>" means I read that file in the worktree (a generated golden, a template or a library source) and the claim is what it says. "not verified" means I did not read it, and the claim rests on the language rule or on a sibling file. Every path under "src/spec/resources/generated" is read at commit `3ed45f1ac` of branch `feat/ogen-designs`, which already contains the Go fix `7ce231c2f` ("fix(go): pass the call context to the trace propagator"). Line numbers are those of that commit.

## Goal

A request must carry the trace context of the caller that made the call, never a context the SDK invents (a background context, a global captured earlier, or a context read on a thread or task the caller did not run on). Go had that fault: `InjectTraceContext(headers)` handed the propagator `context.Background()`, so the caller's span never reached `traceparent`. The audit below shows the other eleven SDKs read the ambient context of the caller at the injection point and do not have the Go fault, but none of them has a test that drives an operation and proves it, so this work adds that proof to all twelve and hardens the one place where the proof would fail in an edge case (rust).

## Owner decisions that bind this work

- Client SDKs only, in twelve languages with the same capabilities and the same API shape; a difference between two languages is a defect until a language feature forces it (root `AGENTS.md`, `generators/AGENTS.md`). So the ambient languages keep their no-context signature, and go keeps `InjectTraceContext(ctx, headers)` because Go has no ambient context.
- No client-side validation, typed errors are thrown and never returned as values, no servers, native types where the language has one. None of these is touched: tracing is best-effort and a failure to inject must never fail a call (the existing `catch`/`rescue` around every injector stays).
- Templates are Mustache files and never read vendor extensions. This work adds no extension and no template logic.
- Never edit `.github/workflows` (suggest only). The tests below need no workflow change; the rust test needs `--all-features`, which the existing suite already uses (verified in `src/spec/resources/generated/rust/src/trace_context_util.rs` line 168-170 and `Cargo.toml` line 72-73).
- The shared test catalogue `src/spec/resources/test-catalogue.txt` holds one behaviour id per behaviour; each language has a test named from the id (`bhv<area><nnn>` in the language's casing) or a documented line in `test-catalogue-exceptions.txt`. The `tracing` area is `tracing001` to `tracing012` today (verified in `test-catalogue.txt` lines 907-918).
- Tests: a unit test mirrors its source file (`BaseApi` behaviour goes in the existing base-api test of each language, the helper in `TraceContextUtil` tests), never a file named after a bug, a finding or a PR. A fix is backed by a test that fails without it and passes with it. A spec drives one command; this repository's generated suites are per-class unit tests, so the new tests live in the base-api tests.
- All twelve goldens are committed current in one change, never a subset (`generators/AGENTS.md`, `DockerFormatter`: local regeneration is flaky for php and swift).
- Decision FD-19: csharp uses the BCL `DistributedContextPropagator`; dart, swift and go register the propagator through a hook because no optional dependency can be detected at run time (verified in `generators/AGENTS.md` line 420). This work keeps those hooks.
- No attribution to any tool in commits, PR text, comments or docs; the PR closes #136 (`Closes #136`) and refs #131.

## The shared behaviour

Catalogue lines to add to `src/spec/resources/test-catalogue.txt`, after `tracing012`, in the existing format `areaNNN | promise`:

```
tracing013 | An operation sends the traceparent of the span that is active in the caller's context
tracing014 | The span still reaches traceparent when building the headers first waits on the credentials
tracing015 | Concurrent operations each send the traceparent of their own caller's span
tracing016 | An operation called with no active span sends no traceparent even when a propagator is configured
```

The promises in prose:

- The span is the one active in the caller's context at the moment the operation is called: the `ctx` argument in go, the current OpenTelemetry context (thread, task, fiber, process or zone) in the other eleven. The SDK never builds a context of its own and never reuses one from an earlier call.
- This holds for every attempt of one call (first send, retry, 401 replay): all attempts carry the same trace id. The two SDKs that rebuild headers per attempt (csharp, rust, elixir, ruby, python, dart) re-read the ambient context and get the same value; java, kotlin, swift and go reuse the first headers. No test is added for this because both give the same observable result (open question 5).
- A call with no active span sends no `traceparent` and no `tracestate`, and an empty `tracestate` is never sent (existing tracing008).
- Tracing stays best-effort: any failure while injecting leaves the request untraced and does not fail the call (existing behaviour, unchanged).

Decision to record in `generators/AGENTS.md` (next free number D95): "Trace context comes from the caller's context: go takes it as the `ctx` argument of `InjectTraceContext`; every other SDK reads the ambient OpenTelemetry context at the injection point, in the caller's thread, task, fiber, process or zone. No SDK builds its own context." It replaces the F021 sentence that the Go fix already removed from `generators/go/AGENTS.md` and the sentence "the other eleven SDKs read an ambient context and need no change" at `go/AGENTS.md` line 299, which becomes a pointer to D95.

## The tests

Each test goes into the existing base-api test of the language (named in the table), inside the `BaseApi` group, using the capturing client the file already defines, and each name carries the id in the language's casing. Each starts a real span from an in-memory SDK (not a hand-written `traceparent` string) and compares the captured request header with `00-<trace id>-<span id>-<flags>` of that span.

- tracing013 (all twelve): the caller makes a span active, calls a petstore operation once (`AddPet` or the language's equivalent, as the Go test already does), and the captured `traceparent` equals the span's. Go: pass the span through `ctx` with `trace.ContextWithSpanContext` and register `propagation.TraceContext{}.Inject` as the propagator, so the test fails for the old `context.Background()` code. This replaces `TestBaseApi_CallContextReachesTheTracePropagator`, renamed `TestBhvTracing013_BaseApi_...` so the id check finds it. It fails on a revert of `7ce231c2f`: `InjectTraceContext(headers)` could not compile with the new test, and with a background context the header is empty.
- tracing014 (kotlin, rust, csharp, node, python, swift, dart): the credential lookup first suspends or hops. Kotlin: an authenticator whose `getAuthHeaders` does `withContext(Dispatchers.Default) {}`, and the caller installs the span through the test's `ThreadContextElement`; asserts the header. Rust: an authenticator whose `try_auth_headers` yields, the operation future is polled once under an `attach()` guard on the test thread, the guard is dropped, and the future is finished on a second thread; asserts the header (fails today, passes with the capture at entry). Csharp: an authenticator that awaits `Task.Delay` with `ConfigureAwait(false)`. Node: an authenticator with a `setTimeout` promise, with the async-hooks context manager registered. Python: an authenticator that is slow (the call is offloaded to a thread, `base_api.py:387`). Swift: an authenticator that does `try await Task.sleep`; the hook reads the test's task-local. Dart: an authenticator that awaits `Future.delayed`; the hook reads the zone value.
- tracing015 (all but php): two operations run concurrently (threads for java, ruby and go; tasks for the async languages; `Task.async` for elixir), each under its own span, and each captured request carries its own `traceparent`; this also fails any implementation that keeps the span in a global.
- tracing016 (all twelve): with the propagator configured (or OpenTelemetry registered), call an operation with no active span (go: `context.Background()`), and the captured headers hold no `traceparent`, after an earlier call in the same test had a span. This guards the stale-context fault (a context kept from a previous call).
- Not tested a second time: the helper tests tracing001 to tracing012 stay in the `TraceContextUtil` tests where they are (unit test mirrors source); nothing is added to those files.

Exceptions to add to `test-catalogue-exceptions.txt` (format `language | id | reason`):

```
java | tracing014 | the call is blocking and builds the headers on the caller's thread, so no suspension or thread change can happen before the span is read; tracing013 covers the path
php | tracing014 | PHP runs one request at a time and has no suspension point in the header path; tracing013 covers the path
php | tracing015 | PHP runs one request at a time in one process, so two operations cannot be in flight together
ruby | tracing014 | the call is blocking and builds the headers on the caller's thread; tracing013 covers the path
go | tracing014 | the caller's context is passed as an explicit argument, so no ambient scope can be lost before the span is read; tracing013 covers the path
elixir | tracing014 | the headers are built in the calling process with no hand-off; tracing013 covers the path
```

Test and generated-name rules to respect: the id is the first `bhv([a-z]+)(\d{3})` of the lower-cased name with separators dropped (verified in `generators/AGENTS.md` line 85), e.g. `bhvTracing013...` (java, kotlin, csharp), `test_bhv_tracing_013_...` (python, rust), `TestBhvTracing013_...` (go), `'bhv tracing 013 ...'` (dart, node), `testBhvTracing013...` (swift), `test "bhv tracing 013 ..."` (elixir), the equivalent in php and ruby (casing not verified; copy the sibling test names in the same file). The unit-test name must also keep `TestParitySpec` quiet: the tests sit in the `BaseApi` group in every language (groups are compared when no id is present; with ids the spec compares by id).

## Risks and open questions

1. Kotlin and a missing coroutine element. Only the `ThreadContextElement` idiom keeps the span across thread changes, and the SDK cannot see the coroutine context's OpenTelemetry element without a new dependency. Recommended answer: no code change and no new dependency; document the idiom in `docs/languages/kotlin.md` and prove it with the test's own element. Reject capturing at entry in kotlin: `TraceContextUtil` is a public `expect object`, so a new parameter would change the public surface (rule: the surface is fixed), and the only case it would fix is an unconfined or undispatched start.
2. Swift's provider. If `opentelemetry-swift` 1.13.0's `activeSpan` is not task-local, the doc example at `TraceContextUtil.swift:18-29` returns the wrong span for an operation. Not verified because the package is not on this machine. Recommended answer: the implementer reads the package source first; if it is not task-aware, change only the doc example (read the span from a task-local the application owns), keep the hook signature, and record the limit in `docs/languages/swift.md`. Do not add a context parameter to the hook (it would diverge from dart, whose hook is the same shape).
3. Dart's `opentelemetry` package. Same shape and same status as risk 2 (package not on this machine, zone-based `Context.current` not verified). Recommended answer: the test proves the mechanism with a plain zone value, and a second test with the real package is added only if reading the package shows `Context.current` is zone-based.
4. Header order (side finding, not part of #136). An injected `traceparent` is written after the per-call headers in go, java, php, python, ruby, node, dart, rust, swift and elixir, so it overwrites a per-call `traceparent` when a span is active; in kotlin (`BaseApi.kt:253`, per-call headers at `:254-260`) and csharp (`BaseApi.cs:298`, per-call headers after) the per-call header wins. The order is not verified for java (it has no per-call header layer in the `BaseApi.java` I read). Recommended answer: open a separate issue; do not widen #136, because the fix needs an owner decision on which side wins.
5. Retries and the 401 replay. The SDKs that rebuild headers per attempt re-read the context, the others reuse the first headers; both give the same trace id because the span is the same. Recommended answer: no extra id; the claim is stated in the shared behaviour and checked by tracing013 only for the first attempt.
6. Rust's capture at entry is the only code change. Risks: it adds a crate-private parameter in two functions (`inject_trace_context` called at `base_api.rs:334` and `:755`), under `#[cfg(feature = "opentelemetry")]` only, so the default build is unchanged; and the new test must be compiled only with the feature. Recommended answer: do it, because the failure it removes is the same class as #136 and is cheap; if the owner prefers zero code, the rust test of tracing014 is dropped and rust gets an exception line.
7. Golden regeneration. The twelve goldens must be committed current in one push (docker formatters are flaky for php and swift; a run takes about 25 minutes). Recommended answer: regenerate in CI-equivalent conditions, commit all twelve, run the per-language specs locally first.
8. Dev-dependency comments. Adding the base-api test as a consumer changes `DEV-DEPENDENCIES` goldens; whether any test checks the comments is not verified. Recommended answer: edit them in the same change and run the golden test.
9. Test heaviness. tracing014 in rust needs a manual poll across threads (`std::future::poll_fn`, `Waker::noop` need a recent toolchain; the crate's minimum Rust version is not verified). Recommended answer: use whatever the crate already uses for polling in tests, otherwise a `std::thread::spawn` plus `block_on`-style helper from `tokio`.
