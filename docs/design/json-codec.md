# JSON codec design (issue #107, item F31 of #131)

Status: proposal for owner review. Nothing here is built. It turns the baseline in [json-performance.md](json-performance.md) and the harness in [../../benchmarks/](../../benchmarks/README.md) into a plan for all twelve SDKs (java, kotlin, csharp, php, python, ruby, node, dart, go, rust, swift, elixir). Every claim about a language names the generated file it was read in; a claim I did not read is marked "not verified". Every verdict that needs a number says which number, and where there is no number yet the plan makes the measurement the first step (the measure-first rule of #131).

## Goal

Make decoding and encoding JSON in each SDK as cheap as the language allows without weakening one promise the serializers make today: where reflection, runtime metadata or repeated passes over the same bytes are the measured slow path, generate straight-line code for each model instead. The work is justified per language by a number from `benchmarks/`, never by a belief, so a language whose serializer is already within noise of a hand-written codec gets no codec and a written reason. The public API, the wire bytes and every error message stay exactly as they are; the only visible change is speed.

## Owner decisions that bind this work

- No client-side validation (S3, D55, #131): the codec checks what the serializer checks today (type, enum, required, `format: uri`, base64, depth) and not one constraint more. It must not turn "tolerate slightly wrong server data" into failures, and must not add a pattern or range check because a generated decoder makes it cheap.
- Typed errors are thrown, never returned as values (#131): a decode failure stays the SDK's `SerializationError` with the canonical message (D15: `Failed to deserialize JSON: <detail>`, `JSON nesting depth <N> exceeds limit 1000`). Go still returns an `error` and rust a `Result`, as `generators/AGENTS.md` already fixes for them.
- Clients only, no servers (#131): there is no server-side decode and nothing here is exposed for one.
- Native types where the language has one (#131, #154 to #157): the codec produces the same field types as today; it never swaps a type for speed.
- Templates never read a spec-sourced vendor extension and are Mustache files (root `AGENTS.md`): the codec is rendered from `.mustache` templates from generator-owned facts that carry no `x-` prefix, computed in Java and passed under `vendorExtensions.prop` and `vendorExtensions.model`, the namespaces `populatePropertyDecorators` already uses in `AbstractBetterCodegen.java`. No `StringBuilder` file content.
- Identical capabilities and the same API shape in twelve languages (root `AGENTS.md`): the codec is internal in all twelve and adds no public member. The public surface of `ObjectSerializer` and of each model is compared by hand before the change merges, because the public-surface guard (#122) does not exist yet.
- Settled decisions that the codec must keep and that are not reopened: D15 (depth cap 1000, one message), D18 (one leading U+FEFF stripped in the shared parse helper), D54 (strict primitives, no coercion), D56 (`readOnly` and `writeOnly` have no wire effect), D63 (a declared property wins over an `additionalProperties` key), D64 (non-discriminated oneOf and anyOf variants tried in declaration order), D84 and D85 (literal `/ < > &`, declaration-order keys on encode), F835 (an unknown enum or discriminator value fails loudly), and the decode-failure behaviour of #135.
- The shared test catalogue (`src/spec/resources/test-catalogue.txt`, one id per behaviour, a test named `bhv<area><nnn>` in every language or a documented exception in `test-catalogue-exceptions.txt`) is the only way a behaviour is required. A codec that passes the whole existing table unchanged, plus the lines below, is the acceptance test.
- Never edit `.github/workflows`. The benchmark run stays manual (`benchmarks/run.sh`), as it is today.
- Declining a codec for a language (java, csharp, and the codec half of python and rust below) is a proposed decline in the sense of #131: it is written down with its number and waits for the owner's yes, one language at a time.

## The shared behaviour

The behaviours the serializers already promise are in the catalogue and stay the acceptance suite unchanged (for example `serializationobject004`, `006`, `051`, `058` to `063`, `120` to `126`, `models004`). The codec adds six lines, in a new area `codec`. Each is a promise a hand-written decoder can silently break and that no existing line pins. The ids are proposals; the wording is final once the owner agrees.

```
codec001 | A key that differs from a declared property name only in letter case is an unknown key, never the property
codec002 | Keys may arrive in any order: required, defaulted and discriminator keys are judged after the whole object is read
codec003 | A string with escapes, a surrogate pair and non-ASCII text decodes to the text it was written from
codec004 | Content after the end of the JSON document is rejected with the SDK's serialization error
codec005 | Doubling the nesting depth of a self-recursive payload makes the decode take less than three times as long
codec006 | A canonical payload that uses every field kind of a model decodes and encodes back to the same bytes
```

What each promises, and why it is a gap today:

- `codec001`. D94 records "exact wire names only" as verified with locks, but no catalogue line carries it. Go has to run `dropMiscasedKeys` (`json_marshal.mustache`) to keep encoding/json from matching `{"NAME":..}` to a field tagged `name`; a generated decoder that switches on the key text gets this for free and a decoder built on a case-folding library would lose it. The assertion: decode `{"Name":"x","name":"y"}` into a model with a `name` property; the property is `y` in all twelve (never `x`, never an error, and the miscased key is ignored or kept as an additional property exactly as an undeclared key is).
- `codec002`. Go's required-key check runs after the whole object is decoded because it re-parses the bytes; a streaming decoder reads keys in order and could judge "required" or "discriminator first" too early. The assertion: the same payload with its keys reversed, and with the discriminator last, decodes to an equal model.
- `codec003`. A hand-written string scanner is where `😀` pairs, `\u0000`, `\/` and a lone surrogate go wrong. The assertion uses one fixed string (a quote, a backslash, `\n`, a pair and an accented letter) in a string field and a map key. The lone-surrogate case is not part of this line: it is an open question under Risks, because the twelve parsers disagree and the line would otherwise invent a rule.
- `codec004`. Rust checks the end of input after the value (`deserializer.end()`), and go's `json.Unmarshal` checks it; a scanner that stops after the closing brace would not. The assertion: `{"name":"x"} 1` and `{"name":"x"}{}` are a `SerializationError`; trailing whitespace is accepted.
- `codec005`. The motivating defect of #107: go decodes the same bytes three or four times per model, so a chain of depth d costs about d squared. The fixture is `TreeNode` (`child` is a `TreeNode`, `value` required; `src/spec/resources/specs/petstore/openapi.yaml`). The test builds the text `{"value":"x","child":` repeated, decodes a chain of depth 250 and of depth 500, takes the best of five timings of each, and asserts that the second is under three times the first. A linear decoder gives about 2, a quadratic one about 4. It measures time, so the threshold is wide, the depths stay under the 1000 cap, and the best-of-five removes scheduler noise (see Risks). It is a guard, not the proof: the proof is the benchmark.
- `codec006`. One fixed Pet-shaped payload in the test template (the `medium.json` shape: nested model, array of models, set of strings, enum, uri, email, double, nullable) is decoded, encoded and compared to the original text. The encoded key order is declaration order (D85), so the payload is written in that order.

Not a new line, on purpose: whether a language passes each of the existing lines is already enforced by `TestParitySpec`. Not a new line either: a "fast enough" assertion. Speed is measured by `benchmarks/run.sh`, and `codec005` is the only guard that can run inside the generated suites without a reference machine.

One candidate is held back until the twelve are read: `codec007 | An integer field rejects a literal written with a fraction or an exponent even when its value is whole (7.0, 1e2)`. Swift enforces it with a second decode (`ObjectSerializer.swift`, the `hasNonIntegralNumber` branch) and `serializationobject120` covers the fractional case, but I did not read the other eleven for `1e2`. If one accepts it today, that is a parity defect to file on its own, not something this work should fix on the way.

## The shared generator changes

All of it is in `src/main/java/io/github/mridang/codegen/generators/` and in `src/test/java/io/github/mridang/codegen/generators/`.

- New `ModelCodecs.java`, a pure class in the style of `ErrorResponses.java` (no language knowledge except what it is asked for). It takes a `CodegenModel` and its properties and returns neutral rows, one per property, in declaration order: wire name, language name, `kind` (string, int32, int64, double, decimal, boolean, date, date-time, time, duration, uuid, uri, byte, binary, enum, model, array, set, map, any, composed), `required`, `nullable`, `hasDefault` with the default literal the language already renders, the element row for an array, set or map, and the flags the serializers already use (`isStrictBase64`, `isAbsoluteUri`). It also returns model-level flags: `hasAdditionalProperties` (and its element kind), `isStrict` (`unevaluatedProperties: false`), `isEnum`, `isComposed`, `isClassicAllOfBase`, `isClassicAllOfChild`. Mustache is logic-less, so each kind is one boolean (`codecIsInt32`, `codecIsModel`, ...) and a template partial per kind renders the decode and encode line.
- `AbstractBetterCodegen.java`: `populatePropertyDecorators` gains the per-property rows under `vendorExtensions.prop.codec`, and `postProcessAllModels` gains one `populateModelCodec` call that fills `vendorExtensions.model.codec`. The pass runs for all twelve whether or not a language renders it, so a language adopts the codec by adding a template and never needs a generator change of its own. A language that does not render it produces a byte-identical golden.
- A new hook `protected boolean emitsModelCodec()`, default `false`, so the golden of a language changes only when its template exists. It mirrors `emitUnitTests()` (line 604).
- The classic `allOf` pass (`markClassicDiscriminatorInheritance`) and the oneOf/anyOf pass already tell a model what it is. The codec keeps them as they are: a composed model and a classic base keep their existing decoder, which for its variants calls the generated codec of the variant (see Risks, scope). `ModelCodecs` marks them `isComposed` or `isClassicAllOfBase` so the template does not render a decoder for them.
- The depth cap. Today every language scans the whole text for the depth before parsing, in the interpreter in most of them (python, ruby, node, dart, elixir, swift, csharp). Where the parser enforces a limit itself (java `StreamReadConstraints`, ruby `max_nesting`, csharp `JsonSerializerOptions.MaxDepth`) the scan is redundant for a payload that passes. The shared rule, written once in `generators/AGENTS.md`: the parser's own limit enforces the cap where the parser has one, and the scan runs only to compute the number for the canonical message after the parser refused, or, where the parser has no limit, only when the text holds more openers than the cap (php already does this: `assertJsonDepth` in `lib/ObjectSerializer.php`). The message and the cap do not change (`serializationobject051` pins both).
- `src/test/java/.../generators/ModelCodecsTest.java` mirrors `ModelCodecs.java` (the unit-test rule: one test file per source file). It asserts the rows for the golden models: a required nullable property, a property with a sibling default, a strict model, a model with `additionalProperties`, an enum, a set, a map of arrays, a composed model.
- No change to `.github/workflows`, to the fixture spec (`TreeNode`, `Pet`, `Tag`, `Category` already exist), or to the public surface.

## Risks and open questions

Only real ones. Each has a recommended answer.

1. **The existing performance page reads four languages wrongly.** `json-performance.md` says kotlin, dart, swift and elixir "are expected not to need" a codec because they already use compile-time mapping, and that ruby was "not read closely enough". The generated sources say otherwise: kotlin decodes the same text three times (`ObjectSerializer.kt`, above), swift runs `JSONDecoder` twice on the medium payload and builds a full tree first, elixir maps by string-keyed metadata, ruby scans in Ruby although the parser has its own limit. Dart's reading holds. A decision taken from the page would skip the languages with the most redundant passes. Recommended: correct the page in the same PR that lands stage 0, and treat those four as "measure first" (they are in the table that way).
2. **Strictness drift: a generated decoder is fast because it is wrong.** The strict-primitive, null-element, enum, discriminator, depth, BOM, duplicate-key and number rules are the whole contract (`json-performance.md` lists them, and D54 and D15 pin them). Recommended: the old path stays in the tree until the new one passes the entire existing ObjectSerializer table plus `codec001` to `codec006` in that language; the PR removes the old path only then; no flag keeps both (a flag doubles the matrix, the root `AGENTS.md` rule on options).
3. **Scope of models.** Composed models (oneOf, anyOf) and the classic allOf base carry hand-written decoders that implement D64 and F835 and are locked by `unions301` to `unions304`. Recommended: the codec covers plain object models, enums, and arrays, sets and maps of them; a composed model and a classic base keep their decoder, and their variants call the generated codec. This is also the order that gets most of the win, since the benchmark payloads are plain models.
4. **Go: own a JSON scanner, or take a dependency.** Stage G2 needs a scanner whose string, number and escape handling matches `encoding/json` where the SDK promises it (duplicate keys keep the last, BOM, invalid UTF-8 text) and rejects what it rejects. A library (ogen's `jx`, `jsoniter`) is a possible way; I did not read their strictness against our contract, so any claim that they match is not verified. Recommended: do G1 first and measure; if G2 is needed, write the scanner as a generated support file in package `models` with a grammar table in `model_test.mustache`, not a dependency, because a dependency's idea of strict is not ours and the go.mod stays small (brotli, klauspost/compress, uuid per `go/AGENTS.md`). The owner may prefer the dependency (the settled rule allows "a small pure library"); that is a question for the owner and I recommend no.
5. **Go G1 might not be enough, or might be.** The doc's 22x is easyjson against our models; multi-pass accounts for only part of it, and a split-once decoder still re-scans nested bytes at every level (one split per level). Recommended gate, to confirm in stage 0 on an idle machine: ship G1 alone if medium decode falls to 25% or less of 34.9 us and `codec005` passes; otherwise G2.
6. **PHP dependencies.** Replacing the Symfony denormalize path for models leaves `symfony/serializer`, `symfony/property-info`, `symfony/property-access` and `phpdocumentor/reflection-docblock` required in the golden `composer.json` with fewer users. Removing them is a visible change for every consumer (install size, and the clients' keep-listed manifests, per the root `AGENTS.md` note about adding a dependency to a generated test). Not verified: which of these the composed-model path, the date normalizers and `Uuid` handling still use. Recommended: the first PR keeps every requirement; a second, separate PR drops what a grep proves unused, with the docs page for php updated.
7. **PHP `ext-ds` and collections.** Models hold `\Ds\Vector`, `\Ds\Set`, `\Ds\Map`; a codec that builds them in a loop is only as fast as the polyfill or extension in use (`composer.json` suggests `ext-ds`, and does not require it). Recommended: measure both in stage 0 and say in `docs/languages/php.md` which was measured; do not require the extension.
8. **Node: class-transformer and the decorators.** The model classes carry `@Expose`, `@Type`, `@Transform` and the SDK depends on class-transformer at runtime (`node/AGENTS.md`). Whether a consumer imports those decorators from the SDK's models for their own use is not verified. Recommended: N2 adds the two statics and leaves the decorators and the dependency in place; removing either is a separate decision, with a deprecation note in `docs/languages/node.md`.
9. **`codec005` measures time.** A timing assertion in a suite that runs in a loaded Docker VM can flake. Recommended: best of five, wide threshold (under 3 where linear is 2 and quadratic is 4), depths 250 and 500 under the cap, and run it once in each language in stage 0 under load to see the real spread before it lands. If a language flakes, the fix is a larger depth, not a looser threshold. The alternative (count allocations) is deterministic in go (`testing.AllocsPerRun`) but not portable: node, php and rust have no portable counter. Recommended: keep timing; add an allocation bound as an extra go-only row in `go/test/model_test.mustache`.
10. **Land per language, or all twelve together.** The root `AGENTS.md` says a change found in one language is applied to all twelve. This one changes no public member and no byte, so staging per language cannot break the harmonised API. Recommended: the tests (stage 0) and the shared generator pass land for all twelve together; each language's codec lands on its own once its number justifies it, with the decision recorded in `generators/AGENTS.md` and `docs/languages/<lang>.md`. Owner to confirm.
11. **The numbers are one noisy run.** Go spreads reach 165% on small payloads, csharp 230%, and python's generated medium decode row has a 123% spread; the machine had a load average of 14 to 18 on 10 cores. Recommended: before any language is committed to stage 2, re-run `benchmarks/run.sh <lang>` alone on an idle machine and record the result in `RESULTS.md`; the order (php, go, node) was large enough to survive noise, the small factors (rust 1.2 to 1.7x) were not.
12. **Lone surrogates and invalid UTF-8.** The twelve parsers disagree on `"\uD800"` and on bytes that are not UTF-8 (encoding/json replaces them, others fail; some not verified). A scanner has to pick one. Recommended: the codec reproduces what each language's own parser does today, since the contract has no line for it; if the owner wants one rule across twelve, that is a new catalogue line with its own parity work, not part of this one.
13. **Encode is in scope only where the number is large.** php (14x) and node (9x) encode share the codec; go encode is within 1.7x on medium and a noisy 7.6x on large (the plain `encoding/json` row is 0.52x of generated on large, which means the SDK's marshal helper costs there, unexplained). Recommended: encode is included for php and node, and for go only after the idle re-run explains the large-payload row.
14. **Per-model generated code grows every golden.** A codec for each model adds lines to 55 Go files, the PHP codec classes, and the node statics. Recommended: accept it (readability of generated output is not a stated goal, correctness and speed are), keep the rendering in partials per kind so the generated code stays regular, and check the goldens' formatter gates (gofumpt, php-cs-fixer, prettier) still pass.

## The order of work and a size per language

Sizes are the pull request effort: S is under a day of template work, M a few days, L about a week or more, each including the golden regeneration of all twelve (the Docker formatters make a local regeneration flaky, so the committed goldens are all twelve, current) and the docs pages.

0. **Stage 0, all twelve, together (the baseline and the tests).** Add `codec001` to `codec006` to the catalogue and one row per line to each of the twelve test templates; run `codec005` once per language as a spike to list the languages that are quadratic today; add runners to `benchmarks/` for kotlin, ruby, dart, swift and elixir (copy a sibling `run.sh`, replace the two calls); re-run everything alone on an idle machine; correct `json-performance.md` and write the new `RESULTS.md`. Docs: `benchmarks/README.md`. Per language: tests S in all twelve; runners S in five.
1. **Cheap shell fixes, one pull request each, each justified by its own number.**
   - python: S (gate the scan; decide the float hook by number).
   - rust: S (count first, scan only above the cap; fold the float check into the encode).
   - node N1: S (reviver only for a decimal field; gate the scan), measured first.
   - ruby: S, if the stage 0 number agrees (drop the Ruby scan, catch `JSON::NestingError`, compute the depth for the message only on failure).
