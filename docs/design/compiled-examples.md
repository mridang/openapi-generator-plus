# Compiled examples design (issue #111, ledger findings F1152 and F1176)

Status: proposal for owner review. Nothing here is built. This document fixes one shape for all twelve SDKs (java, kotlin, csharp, php, python, ruby, node, dart, go, rust, swift, elixir) so that no language is built first and the other eleven made to follow. Issue #111 has two halves: compiling the README and SKILLS fences, and a minimum-runtime matrix for six languages. This design covers the first half only; the matrix is proposed as its own issue (see the risks).

Evidence marks: "verified in <file>" means the file was read for this design; "not verified" means it was not read, and the implementer must read it first.

## Goal

Every code example a generated SDK shows its users, in `README.md`, in `SKILLS.md` and in one published `examples/quickstart` program, is built by a gate in the golden's own toolchain, so an example can no longer stop compiling without a test failing. Each SDK publishes one complete, runnable example (`examples/quickstart`) that is the same program in all twelve languages, differing only by idiom, and the golden spec runs it against the shared mock server. The gates run inside the existing Docker specs, found by the existing `*Spec.java` include in `pom.xml` (verified in pom.xml and `.github/workflows/test.yml`, which runs `mvn verify`), so no file under `.github/workflows` changes.

## Owner decisions that bind this work

- Client SDKs only, twelve languages, identical capabilities and the same API shape; a difference between two languages is a defect until a named language feature forces it (root `AGENTS.md`, shared `generators/AGENTS.md`). So the quickstart does the same steps everywhere and the fence rules are one rule for all twelve.
- No client-side validation, typed errors are thrown and never returned as values, no servers, native types where the language has one. The quickstart builds a client, makes one call and closes the client; it adds no validation and no result wrapper, and any error escapes as the SDK's own typed error.
- Templates never read spec-sourced vendor extensions and are Mustache files. A value the generator must compute (the example operation) is computed in Java and handed over under a generator-owned name with no `x-` prefix, the way `vendorExtensions.op.signatureArgs` is today (verified in `AbstractBetterCodegen.java` around line 3852). No example or harness content is built with `StringBuilder`.
- Never edit `.github/workflows`. The gates are `*Spec.java` classes that `mvn verify` already includes; a new language-level target is a Makefile target, never a workflow step.
- The shared test catalogue `src/spec/resources/test-catalogue.txt`: one behaviour id per behaviour, each language has a test carrying `bhv<area><nnn>` or a documented line in `test-catalogue-exceptions.txt` (verified in `TestCatalogue.java` and the shared `AGENTS.md`, section "Test parity check").
- Do not add test files: extend the test templates that exist (shared `AGENTS.md`, "Test layout"). A fix needs a test that fails without it. Goldens are regenerated, never hand-edited, and all twelve are committed current.
- Generated prose is character-level aligned across the twelve and every example in it "compiles and runs as written" (root `AGENTS.md`, "Template and generated-prose rules"). This design is how that rule becomes a gate.
- No petstore vocabulary in templates; `FixtureVocabularyLeakTest` fails on it. Operation, model and package names in examples come from the spec, never from a literal.
- No `//` comments in php and csharp templates, no HTML entities, no inline lint suppressions, no whole-tool disables (build-breaking rules in the shared `AGENTS.md`). Examples are generated files and obey the same rules.
- Environment variable names differ by language and by package and are listed on each language page (verified in `docs/decisions.md`, "Credentials come from an argument, then the environment"). The quickstart uses the names its own README documents; it does not reopen that decision.

## The shared behaviour

What exists today (verified): only three languages have a README test (`go/test/readme_test.mustache`, `java/test/ReadmeTest.mustache`, `ruby/test/readme_test.mustache`), and they check by substring and section order. The python test parses one SKILLS fence with `ast.parse` and pins one argument (verified in `python/test/test_metadata.mustache`). No test in any language compiles a fence. A fence is a fragment today: `return err` outside a function and undeclared `pet`/`authenticator` in go (verified in `go/README.md`, `go/SKILLS.md`), `?` and `use` at top level and undeclared `pet` in rust (verified in `rust/SKILLS.md`), `client` never declared in python SKILLS (verified in `python/SKILLS.md`), `$body` never declared in the php README (verified in `php/README.md`), `...` placeholders in java SKILLS (verified in `java/SKILLS.md`). Two defects found while reading, both of which the gate would have caught: the java README line 41 and SKILLS lines 291 and 350 call `new Pet()`, but the generated `Pet` has one public constructor `Pet(String name, Set<String> photoUrls)` and a private builder constructor (verified in `java/src/main/java/com/example/petstore/models/Pet.java` lines 188 and 195); and the node README quick start uses `Pet` without importing it (verified in `node/README.md`, section "Quick start", which is also the one README whose heading is not "Usage").

New catalogue lines, a new area `examples` (the area is lower-case letters followed by three digits, as in `TestCatalogue`):

```
examples001 | A generated SDK ships examples/quickstart, one complete program that builds a client, calls one operation and closes the client
examples002 | The quickstart takes the host and the token from the environment variables its README names and holds no literal credential
examples003 | The README Usage fence and the quickstart hold the same statements, line for line, whatever the imports
examples004 | Every fence in README.md and SKILLS.md tagged with the SDK language declares its kind, file or statements, and declares everything it uses
examples005 | No fence tagged with the SDK language holds a placeholder line such as an ellipsis, a bare angle-bracket name or a mention of an undeclared variable named in the shared ambient list
examples006 | The SDK Makefile has an examples target that builds every file under examples
```

Promises that are not catalogue lines because they are build gates run by Docker specs, not by the SDK's own test suite (exit code asserted, as the shared `AGENTS.md` demands for spec gates):

- `make examples` builds the quickstart with the language's own compiler or type checker and fails on any error.
- `make examples-run` runs the quickstart with the variables the Makefile maps from `API_BASE_URL` (verified in `SharedHelperContainers.java` line 97 that `API_BASE_URL` is the Chasm HTTP URL) and exits 0. Run only in the golden spec; real clients have no mock server.
- Every fence of the SDK language tag in `README.md` and `SKILLS.md` builds when wrapped by the language's harness, never executed.

The fence contract that makes the gate possible (one rule for all twelve, written once in the shared `AGENTS.md`):

1. The compiled set is every fence whose tag equals the SDK language (`go`, `rust`, `typescript` for node, and so on, verified by counting tags in all twelve READMEs and SKILLS files). Fences tagged `bash`, `toml`, `xml`, `yaml`, `groovy`, `good` and `bad` are not source and are not compiled. A fence that cannot compile must not carry the language tag; there is no skip list.
2. A fence declares its kind on the info string after the language word: `file` (a compilation unit body: imports and declarations, no statements outside a function) or `statements` (a statement list with its imports on top). Renderers show only the first word; whether every renderer used by the registries ignores the rest is not verified. A fence mixing the two (the go fake authenticator, which declares a type and methods and then a `client :=` statement, verified in `go/SKILLS.md`) is split by the template author.
3. A fence is self-contained: it declares or imports everything it uses. There is no ambient `client`, `authenticator`, `transport` or `pet`. A fence that calls an operation does it from a function that takes the operation's own parameters as typed arguments, the form php, ruby, dart and kotlin already use (verified: `addPetOrReport(Client $client, ...)` in `php/SKILLS.md`, `suspend fun addPetOrReport(client: Client, pet: Pet)` in `kotlin/SKILLS.md`). It never builds a model from nothing, so a model whose constructor needs required properties cannot break it. The go, rust, swift and elixir fences switch to this form; java, node and python lose `new Pet()` and `Pet.model_construct()`.
4. The harness wraps, it never repairs: it adds the file shell, hoists imports where the language needs them at the top, and nothing else.

## The shared generator changes

Files, and what changes. Every change lands for all twelve with all twelve goldens regenerated and committed current (shared `AGENTS.md`, "Before you push").

1. `src/main/java/io/github/mridang/codegen/generators/AbstractBetterCodegen.java`
   - New boolean option `generateExamples`, next to `generateTests` and `generateUnitTests` (verified lines 231 to 240). Default `false`, so a real client (the six Zitadel SDKs keep their hand-written files in `.openapi-generator-ignore`, verified in root `AGENTS.md`) gets no new directory until it opts in. `ClientGenerator.java` in `src/test` already sets `generateTests` to `true` for goldens (verified line 62) and sets this one too.
   - A generator-owned example operation, chosen once in `processOpenAPI` after the normalisation rules (`DropInternalOperationsRule` and `MultipleSuccessResponsesRule` run there, verified), so a dropped `x-internal` operation or a synthesised union is never picked wrongly: the first operation in spec order with no required path, query, header, cookie or body parameter and no required security. Surfaced on the operation decorator next to `signatureArgs` as `vendorExtensions.op.isExampleOperation`, and as `additionalProperties.hasExampleOperation` for the template to branch on. When no operation qualifies (the probe spec's only operations are POSTs with a body, verified in `specs/probe/openapi.yaml`), the quickstart builds the client and closes it, and says in its prose that the spec has no zero-input operation. In the petstore golden `getInventory` qualifies (no parameters, `security: []`, verified in `specs/petstore/openapi.yaml` line 1106); it is not the first operation, so README fences that use the first operation (`addPet`) keep calling it through the typed-function form.
   - The environment variable names for the quickstart come from the values each language's README already renders (`envVarPrefix` or `envPrefix`, verified: go uses `{{envVarPrefix}}`, rust and python use `{{envPrefix}}` in their readme templates). No new naming rule.
   - New supporting file registration for `examples/` through the existing `getSupportingFileSpecs()` hook (verified at line 563), gated on `generateExamples`, in each `Better<Lang>Codegen.java`.
2. Per language, new template `templates/<lang>/examples/quickstart.mustache` (path and name per idiom; see the table), plus a shared partial per language `usage_statements.mustache` that holds the statements of the README Usage fence. The README and the quickstart both include that partial, so they cannot drift (this is what `examples003` checks). Only the imports and the file shell differ between the two.
3. Per language `makefile.mustache`: two new phony targets `examples` and `examples-run`. `examples-run` maps `API_BASE_URL` to the language's own base-URL variable and sets a placeholder token, and runs only the quickstart. Existing targets (`lint`, `typecheck`, `docs`) are widened or told to skip `examples/` only where the table says so.
4. Per language `readme.mustache` and `skills.mustache`: add the kind token to every language-tagged fence, split mixed fences, declare what each fence uses, remove placeholders, fix the defects named above, make the Usage fence the shared partial. Section order and headings stay the shared ones (the node "Quick start" heading becomes "Usage", which the other eleven already carry; the go test pins that order, verified in `go/test/readme_test.go`).
5. Per language manifest or type-checker config where the table says the examples are not picked up by the existing build (pom, gradle, csproj, `Package.swift`, tsconfig, Steepfile, `mix.exs`, phpstan config).
6. Spec side (no generator output): `src/spec/java/io/github/mridang/codegen/spec/AbstractExamplesSpec.java` (like `AbstractDocsSpec`, verified, but with three tests: build, run, fences), twelve thin `<Lang>ExamplesSpec` classes (like the existing `<Lang>DocsSpec`, verified for go, rust, node, python), `src/spec/java/.../spec/fences/FenceExtractor.java` (reads a markdown file, returns language-tagged fences with their kind and the heading above them) and `FenceHarness.java` (per-language data: file name, shell, import-hoisting rule, build command). Unit test `src/test/java/.../spec/fences/FenceExtractorTest.java`, mirroring how `TestNameNormaliserTest` and `TestCatalogueTest` sit under `src/test` (verified). The harness writes its files into the container with the commands array (base64 into `/work/.out/fences`), because `/work` is restored from a snapshot before every spec method and `.out` is dropped from the copy (verified in `SharedRuntimeContainer.java` lines 238 and 279).
7. Docs in the same change (root `AGENTS.md` rule): `docs/how-it-works.md` (gates section), the twelve `docs/languages/<lang>.md` (one line each about `examples/`), `docs/decisions.md` (a new short section "Examples are compiled"), the shared `AGENTS.md` (the fence contract, the decision, the gate lesson), and each language's own `AGENTS.md` for its harness quirks.

## The tests

| examples003 | Every non-import line of the README Usage fence appears, in order, in the example file. |
| examples004 | Every fence tagged with the SDK language in `README.md` and `SKILLS.md` carries `file` or `statements` on its info string; a fence of another kind that is tagged with the language fails; the heading of every one is reported on failure. |
| examples005 | No language-tagged fence has a line that is only `...`, a `<Name>` placeholder outside a string, or a call that passes a model created from nothing (the per-language construct list is data in the test, for example `new Pet()` or `model_construct()` pinned as absent; the model name comes from the spec at generation). |
| examples006 | The Makefile has an `examples` target and an `examples-run` target, and the `examples` target names the `examples` directory. |

Docker specs (not catalogue lines; one class per language, three methods, exit code asserted):

- `<Lang>ExamplesSpec.generatedExamplesShouldBuild`: runs `make examples` in the shared runtime container and fails when it exits non-zero; the failure message prints the build output. This is the check that fails when an example stops compiling.
- `<Lang>ExamplesSpec.quickstartShouldRunAgainstTheMockServer`: runs `make examples-run`; the Chasm container answers `getInventory` from the spec alone, which the fixture rule in the shared `AGENTS.md` guarantees ("every new operation answers from the spec alone").
- `<Lang>ExamplesSpec.readmeAndSkillsFencesShouldBuild`: `FenceExtractor` reads `README.md` and `SKILLS.md` from the golden, `FenceHarness` wraps every language-tagged fence (statements into the language's function shell, imports hoisted where the language needs it, files with only the header), writes the files under `/work/.out/fences` through the exec commands, and builds them against the SDK with the same compiler or type checker `make examples` uses. A failure names the file, the heading and the fence number.
- Unit: `FenceExtractorTest` (info-string parsing, the `good` and `bad` fences are ignored, an unclosed fence fails loudly, the heading above a fence is reported). Generator side: a test in `src/test/java/.../generators` generates the probe spec (verified: `ProbeGenerator` exists and does not set `generateTests`) with `generateExamples` on, and asserts that with no zero-input operation the quickstart omits the call, that no petstore word appears (the existing `FixtureVocabularyLeakTest` extended, not a new class), and that the chosen example operation is the first qualifying one in spec order.

Each fix is backed by a test that fails without it: for the java `new Pet()` defect the fences gate fails on the java README today, which is the proof that the gate is non-vacuous, and the first commit of stage 1 (below) records that failure.

## Risks and open questions

1. Rewriting the fences is the bulk of the work, and it is hand work. Roughly 17 to 26 language-tagged fences per language (counted from the READMEs and SKILLS files: 21 in java, 24 in kotlin, 17 in csharp, 22 in php, 22 in python, 25 in ruby, 24 in node, 22 in dart, 22 in go, 18 in rust, 20 in swift, 26 in elixir), about 260 in total, each to be classified, made self-contained and split where mixed. Recommendation: do it language by language in the same change as that language's example, keep the prose character-aligned, and let the gate list the failing fences so none is guessed.
2. Real specs, not only the petstore golden. The golden has a zero-input operation; a real spec (the probe spec, a gRPC-gateway style spec with only POST bodies) may not. Recommendation: the typed-function form removes the need to build a model, the quickstart falls back to client-and-close, and the probe spec is generated and asserted on at generator level; do not build probe SDKs in Docker now (it doubles the Docker time of every language for a gate that the typed-function form already makes spec independent). Revisit if a real client breaks on a fence.
3. Docker time and size. A new method per language adds one more `cp -a` restore and a build; the shared cache environment (`CARGO_TARGET_DIR`, `GOCACHE`, `MAVEN_OPTS`, verified in the `<Lang>Spec` interfaces) keeps rebuilds cheap, and `test.yml` already warns that the images take about 12 GB. Recommendation: no new images; the examples build in the language's existing image.
4. The new directory now sits under every existing gate. `golangci-lint ./...`, `cargo clippy --all-targets`, `dart analyze`, `dotnet format`, `ktlintCheck`, `detekt` and checkstyle will see the example, and a rule an example cannot meet must not be suppressed (shared `AGENTS.md`, G5 and "Never weaken a linter"). Recommendation: write the example to pass; if a lint cannot be met for a reason the language forces, name it once in the shipped config, as the rule asks.
5. Opt-in for real clients. A new `examples/` directory would appear in the six real clients (verified in root `AGENTS.md`: each lists hand-written files in `.openapi-generator-ignore`). Recommendation: `generateExamples` defaults to `false`, goldens set it to `true`, a client opts in when it is ready to keep the directory.
6. Issue #111 also asks for a minimum-runtime matrix for node, rust, elixir, python, kotlin and csharp. Recommendation: split it into its own issue; it changes the image pins in the `<Lang>Spec` interfaces (one image per language today, verified for go, rust, java, csharp, python, ruby, node, elixir) and the 12 GB image budget, and nothing in this design depends on it.
7. Info-string tokens (`file`, `statements`) must survive every registry's renderer. Recommendation: keep them, since the first word is the only one renderers use for highlighting; verify on GitHub, npm and crates.io pages in stage 0, and if one drops the block, move the kind to a preceding HTML comment, which the extractor can read just as well.
8. Folder name. Dart's registry shows an `example/` folder; every other language is neutral. Recommendation: `examples/` everywhere, one name in all twelve, because the owner rule treats a difference as a defect until a language feature forces it and no build breaks without `example/`.
9. Running the quickstart needs a token the mock does not check. Recommendation: `getInventory` has `security: []` (verified), the Makefile passes a placeholder token, and the example operation selection already refuses an operation with required security.
10. The env variable names of the quickstart cannot be one string across languages (go `SWAGGER_PETSTORE_OPEN_API_3_0_TOKEN`, python `..._ACCESS_TOKEN`, rust `PETSTORE_ACCESS_TOKEN`; verified in the three READMEs). Recommendation: leave that settled difference alone; the Makefile maps the one `API_BASE_URL` of the spec to each language's own name, so `AbstractExamplesSpec` stays free of per-language names.

## The order of work and a size per language

Stage 0 (shared, size L): `generateExamples`, the example-operation selection, the fence contract written into the shared `AGENTS.md`, the six catalogue lines, `AbstractExamplesSpec`, `FenceExtractor`, `FenceHarness`, `FenceExtractorTest`, the docs pages. Nothing here changes a golden by itself.

Stage 1, the pilot, to prove both gates before the rest: go and python. They are the cheapest (no manifest edit) and between them cover a compiled language with import hoisting and a language where the Usage fence is already a program. Commit the failing gate first (it must fail on the current README fences), then the fixes, then regenerate all twelve goldens.

Stage 2: node, ruby, php, dart. These need a config line (tsconfig, Steepfile, phpstan paths) or nothing, and no new build tool.

Stage 3: rust, elixir, swift. The rust gate is only meaningful on CI (amd64); elixir needs the `mix.exs` path and a weaker, documented gate; swift needs the `Package.swift` target.

Stage 4: java, kotlin, csharp. These carry the build-system wiring and the strictest analyzers.

Each stage is one push after its languages' specs pass locally (`etc/ci-local.sh check <Lang...>`), per the working method; CI decides.
