# Design: a required nullable query parameter is sent with an empty value (issue #148)

Status: proposal. Nothing in this file is implemented. "Verified in <file>" means the claim was read in that file of the worktree `designs` (branch `feat/ogen-designs`); "not verified" means it was inferred from a sibling language or from the shared generator and must be read before coding.

## Goal

A query parameter that the spec marks both `required` and nullable must always reach the wire: when its value is null the SDK sends the key with an empty value (`?note=`), the same way a required non-null parameter is always sent, so the contract "a required parameter is always present" holds. Today no SDK does this. Node refuses the call and the other SDKs either refuse it or cannot express the null, which is a stricter failure than the silent drop the issue describes. The change adds one fixture operation, one shared decorator, one template branch per language and four catalogue behaviours.

## What the code does today (read, not run)

* The issue text says the Node value serializer returns nothing for a null query value. That is true of `ValueSerializer.serialize` and `serializeStyled` (verified in `src/main/resources/templates/node/value_serializer.mustache`, the `location === 'query'` early returns), but the generated operation never reaches it with a null required value: the required guard throws first (`options?.<name> == null` raises `TypeError "Missing the required parameter ..."`, verified in `templates/node/api/apis.mustache` lines 219-225). So for a required nullable parameter Node refuses the call; it does not drop the key. The fix still has to touch both the guard and the emission.
* Node is the only language whose options template marks nullable at all (`{{#isNullable}} | null{{/isNullable}}`, verified in `templates/node/api/options.mustache` line 32). The other options templates type a parameter with the plain `{{{dataType}}}`, so a typed language cannot even pass null for a required nullable parameter today (java accepts null but its guard throws, verified in `templates/java/api/api.mustache` lines 335-342).
* The petstore fixture has no nullable parameter at all: the only nullable shape is the model property `RequiredNullable.note` (verified in `src/spec/resources/specs/petstore/openapi.yaml` line 2785). That is why no test noticed.
* An empty value already reaches the wire as `key=` in every language: catalogue `serializationwire016` (empty string param is in the query string) and `operations040` (explicit empty `status` sends the key). The new behaviour reuses that path by putting an empty string where the null was; it does not touch any serializer. Per-language confirmation that `""` in the query container serializes to `key=` is not verified beyond those catalogue lines.
* The generator already knows the flag. Upstream `DefaultCodegen.fromParameter` sets `CodegenParameter.isNullable = true` when the parameter schema is nullable (verified in the openapi-generator 7.22.0 sources jar, `DefaultCodegen.java` line 5466), and the stock normaliser turns `type: [string, "null"]` into that flag. The repository's own `NormalizeOas31NullableTypeRule` was never called and was removed in #100.

## Owner decisions that bind this work

* Client SDKs only, twelve languages (java kotlin csharp php python ruby node dart go rust swift elixir), identical capabilities and the same API shape; a difference between two languages is a defect until a named language feature forces it (root `AGENTS.md`, shared `generators/AGENTS.md`).
* No client-side validation of schema constraints. This change removes a refusal; it adds none. The existing RF-16 rule (a required string must not be empty, except `allowEmptyValue` query parameters) is not changed (see risk 2).
* Typed errors are thrown, never returned as values. A required nullable parameter that is null is not an error, so no new error type is needed; the refusals that remain keep their current type and message.
* No servers, native types where the language has one: a required nullable parameter is typed with the language's own nullable form (see the table), with no generator-owned wrapper (F834).
* Templates are Mustache files and never depend on a spec-sourced `x-*` extension. A flag the generator computes is handed over through `vendorExtensions` under a name without the `x-` prefix, which root `AGENTS.md` (line 44) names as the sanctioned mechanism; `queryStyledAllowEmpty` is the precedent. Native fields (`{{required}}`, `{{isNullable}}`) are used wherever they are enough.
* Required plus nullable keeps the key: S5 / D66 already say this for model properties and `docs/decisions.md` ("Optional and nullable are not told apart on the way out") says a required nullable property is always written. This design extends the same promise to query parameters.
* Never edit `.github/workflows`. The fixture lives only in `src/spec/resources/specs/petstore/openapi.yaml`, nothing is removed or renamed, and a new operation answers from the spec alone.
* Shared test catalogue (`src/spec/resources/test-catalogue.txt`): one behaviour id per behaviour, every language has a test named from the id or a documented line in `test-catalogue-exceptions.txt`. No new test files: extend the existing test templates. A fix is backed by a test that fails without it. All twelve goldens are regenerated and committed current in the same commit as the template change.
* README and docs are part of the change (root `AGENTS.md`, "README and docs are part of every change").

## The shared behaviour

Scope: a query parameter that is `required` and nullable, serialized from a `schema:` (the styled path). `content:` parameters and `deepObject` parameters are out of scope (see risk 3). Header, cookie and path parameters are out of scope (see risk 4).

Proposed catalogue lines (all in area `operations`, appended after `operations124`; the format is `areaNNN | promise`, optional `| multi`):

```
operations125 | Get pet by note sends a null required nullable query parameter as an empty value
operations126 | Get pet by note sends every null required nullable query parameter as an empty value in declaration order
operations127 | Get pet by note sends a non-null required nullable query parameter with its value
operations128 | Get pet by name with a null required query parameter that is not nullable still refuses before sending
```

The exact promises, in prose:

1. P1 (`operations125`): when a required nullable query parameter is null, the request carries the key, an equals sign and nothing after it (`note=`). The call is not refused and the key is not dropped.
2. P2 (`operations126`): several null required nullable parameters are all sent, in declaration order (D53), so `note=&rank=` for the fixture.
3. P3 (`operations127`): when the value is not null the wire is exactly what a required non-nullable parameter would send (style, explode, allowReserved, D52 encoding). The new branch is only taken for null.
4. P4 (`operations128`): a required parameter that is not nullable still refuses null with the current message, `Missing the required parameter '<name>' when calling <Class>.<operation>`. The change must not loosen the guard for the 100 percent of specs that have no nullable parameter.
5. Unchanged and already in the catalogue: an optional parameter that is null or absent sends no key (`operations041`, `serializationwire010`), an explicit empty string sends `key=` (`serializationwire016`, `operations040`), and an empty required string is refused (`operations049`, RF-16). These are the regression guards for the new branch and must stay green.

Where the languages cannot express a promise, the exception goes in `test-catalogue-exceptions.txt` with the forcing feature (table below, column "limit").

### Fixture addition (proposed text, in `petstore/openapi.yaml`, tag `pet`, next to `getPetByName`)

```yaml
  /pet/byNote:
    get:
      tags:
        - pet
      summary: Look up a pet by note (required query parameters whose value may be null)
      operationId: getPetByNote
      parameters:
        - name: note
          in: query
          required: true
          schema:
            type:
              - string
              - "null"
        - name: rank
          in: query
          required: true
          schema:
            type:
              - integer
              - "null"
      responses:
        '200':
          description: OK
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Pet'
```

Two parameters on purpose: one string and one integer, so the typed languages prove a pointer or optional of a non-string type, and two nulls prove the declaration order. The pet tag is chosen because every language already has a pet test template with a recording client (the `operations065` test lives there). The `probe` spec (OAS 3.0.3) also gets one required `nullable: true` query parameter so both spellings of nullable feed the same flag; that file is generated without tests, so only the shipped templates are exercised (`FixtureVocabularyLeakTest` keeps guarding that nothing is hardcoded).

## The shared generator changes

All in `src/main/java/io/github/mridang/codegen/generators/AbstractBetterCodegen.java`; no language Codegen class changes (not verified for every `Better*Codegen`: grep the twelve for an override of `populateParameterDecorators` first).

1. `deriveQuerySerializationKind` (private static, line 4449): add a fifth kind `"requiredNullable"`, returned after the `deepObject` and `content` checks and before `isAllowEmptyValue`, when `param.isQueryParam && param.required && param.isNullable`. Precedence matters: deepObject and content keep winning (out of scope), and requiredNullable beats `styledAllowEmpty` because a null must be sent whatever `allowEmptyValue` says.
2. `populateParameterDecorators` (line 4068): add the boolean mirror `d.put("queryRequiredNullable", "requiredNullable".equals(kind))` beside `queryStyled`. Because the kinds are mutually exclusive, the existing `queryStyled` and `queryStyledAllowEmpty` blocks in every template stop matching a required nullable parameter automatically, so no template needs a `^` guard on them. Update the javadoc that lists the kinds (line 4440 and the "Phase 1.5" comment at line 4080).
3. Nothing else is shared: no new op-level flag (`getOperationContextFlags` is untouched), no change to `optionsParamRequired` (a required nullable parameter still makes the Options object required), no change to `ValueSerializer` in any language.
4. Unit test (mirror rule, the file that already holds the parameter decorator cases is `src/test/java/io/github/mridang/codegen/generators/OperationDecoratorTest.java`, verified, it calls `populateParameterDecorators` at lines 304 and 331): rows for required nullable query (kind `requiredNullable`), optional nullable query (still `styled`), required non-nullable query (still `styled`), required nullable with `allowEmptyValue` (`requiredNullable`), required nullable deepObject (still `deepObject`), required nullable `content` (still `content`), required nullable header (not a query kind). The first row also proves `isNullable` survives to the decorator for both the 3.1 `type: [string, "null"]` and the 3.0 `nullable: true` spelling.

Per-template change, the same in all twelve (the table has the file and the idiom):

* A. Options template: the field and constructor type of a required nullable parameter becomes the language's nullable form, with no default (the absence of a default is what keeps it required, as S5 does for models).
* B. Required guard in the api template: for a required nullable parameter the null test is dropped (`{{^isNullable}}` around it); the RF-16 empty-string test stays (risk 2).
* C. Query emission: a new `{{#vendorExtensions.param.queryRequiredNullable}}` block that emits the normal styled expression when the value is non-null and puts the empty string under the parameter's wire name when it is null.
* D. README template: one sentence in the existing optional/nullable section (the heading differs per language: node `Optional versus nullable`, java `Optional and nullable are one null`, kotlin `Optional and nullable`, php `Optional and nullable are one`, ruby `Optional and nullable are not told apart`, dart `Optional and nullable are one type`, python/go/elixir a bullet, csharp/swift/rust as node; verified by grep in the twelve `readme.mustache` files).

Docs changed in the same pull request: `docs/decisions.md` (a short paragraph under "Optional and nullable are not told apart on the way out"), `docs/types.md` (line 39, one sentence), the shared `generators/AGENTS.md` (S5 gets a second paragraph, and a new D95 row in the "Query, form, path and parameters" table after D53), and the twelve `generators/<lang>/AGENTS.md` files only where the language has a rule of its own to record (go, rust, python, node, elixir, dart; the others need nothing beyond the shared line). The `docs/languages/<lang>.md` pages were not read; update them only if they carry a parameter type table (not verified).

## Risks and open questions

1. Dynamic languages cannot tell an omitted required key from null (node, elixir; python, ruby and php fail at construction when the argument is missing). Recommendation: accept it and say so in the node and elixir READMEs; both send `note=`. Reason: the type (TypeScript) or the struct default already makes the caller state the key, and refusing `undefined` would make the node guard the one place where null and undefined differ.
2. Empty string for a required nullable string. RF-16 refuses `""` for a required string, so `null` would be sendable but `""` (same wire) not. Recommendation: keep RF-16 unchanged and refuse `""`. Reason: loosening later is additive, tightening later is breaking, and no spec author asked for it. If the owner prefers consistency, the alternative is to treat a required nullable string like an `allowEmptyValue` query parameter (one more `{{^isNullable}}` on the existing empty test, in all twelve).
3. `content:` and `deepObject` required nullable parameters. A null JSON value has no obvious empty form and a null deepObject has no key to send. Recommendation: out of scope; they keep today's behaviour (null refused by the guard, because the guard change only applies to the new kind) and the decorator unit test pins that. Write the limit into D95. File a follow-up issue only if a real spec needs it.
4. Required nullable header, cookie and form parameters have the same drop-or-refuse shape (`headerParams` blocks emit only when non-null, verified in node and java templates). A null path parameter cannot be sent at all (an empty segment changes the route), so it stays refused. Recommendation: query only in this change, and open one follow-up issue for header and cookie so the twelve templates are not changed twice. The issue title and the Orval comparison are about query.
5. The wire form of null. `note=` (key, equals sign, empty value) is what the issue asks for and what Orval does; some servers treat a bare `note` differently. Recommendation: `note=`, because it reuses the existing `serializationwire016` path and encodes identically to an empty string.
6. The mock server. Chasm answers from the spec and may validate `rank=` as an integer. Recommendation: every new test asserts on the recorded request only, never on a response from Chasm; the fixture response is a plain `Pet` example. Prove it once by running one language's spec before regenerating the other eleven.
7. Other spellings of nullable. `anyOf: [{type: string}, {type: "null"}]` and a `$ref` to a nullable component schema are not handled by the code path read here (the type array is handled by the stock normaliser; the other spellings are not verified). Recommendation: document that only `type: [T, "null"]` and `nullable: true` are recognised; an unrecognised spelling behaves as today.
8. Public API shape. The options type of an operation with a required nullable parameter changes versus what it would have been, but no existing fixture or user spec could use such an operation before (the call was refused), so the change is additive. The API-surface guard (#122) does not exist yet, so compare the twelve options types by hand once the goldens are regenerated.
9. Golden churn and flaky Docker formatters: regenerating twelve languages locally can show spurious php and swift drift (see the repository's own notes on Docker formatters). Commit all twelve goldens current in one commit and check `git status` for 100 or more unrelated files before pushing.
10. The issue's premise differs from the code (Node refuses, it does not drop). Recommendation: say so in the pull request description and close #148 from the PR that completes the last language (`Closes #148`), not an earlier one.
