# Mockable client design (the ogen Invoker equivalent, item of #131, surface rules of #122)

Status: proposal for owner review. Nothing here is built, and no existing file is changed by this document. It fixes one shape for all twelve SDKs (java, kotlin, csharp, php, python, ruby, node, dart, go, rust, swift, elixir) so that no language is done first and the other eleven made to follow.

A note on the numbers. The task that asked for this design called the topic "issue #122". Issue #122 is the API surface guard (snapshots, exports, third-party leaks). The mockable-client work is the checklist line "Mockable top-level client interface (Invoker equivalent)" in the Go parity issue #131, under "Adopt in a subset of languages", effort S, Go only. #122 matters here because the names this design adds are exactly what its snapshots will record, and its leak rule applies to them. This design widens the #131 line from Go to all twelve, as the task requires; the owner has to confirm the widening (see the risks).

Evidence marks used below: "verified in <file>" means I read that file in the worktree (generated golden or template) and the claim is what it says. "not verified" means I did not read the file or did not compile the idea, and the claim rests on the language rule or on a sibling file.

## Goal

Every SDK lets a user replace the generated client with a hand-written fake in their own tests, without a mocking library, a network or a subclass of generated code. The unit of faking is the API group (the per-tag class), which has an interface, a protocol, a trait or a behaviour in every language, and the top-level client exposes its groups through an interface where the language can state that. The public API of the real client does not change: names and signatures that exist today stay, and the interfaces are additive.

## Owner decisions that bind this work

- Client SDKs only, twelve languages, identical capabilities, the same API shape (parameter order, how a client is created, how options, errors, cancellation are used), expressed in each language's idiom (root `AGENTS.md`). A mock seam present in one language and absent in another is a defect unless a named language feature forces it.
- The public API shape is fixed now so that later work is additive and never breaking (root `AGENTS.md`). So the new interfaces are added next to the existing classes; no class is renamed and no operation signature moves.
- Typed errors are thrown, never returned as values (the error contract in `generators/AGENTS.md`). A fake raises the SDK's own typed error, and the interface signatures do not turn errors into return values. Elixir keeps its `{:ok, _} | {:error, _}` plus bang shape, which is already the settled idiom there (verified in `api/pet_api.ex`, `add_pet` and `add_pet!`).
- No client-side validation (F316). The interface adds no checks.
- Native types where the language has one. Interface signatures use the same types as the class (verified for go in `pkg/pet_api.go`: `*opts.AddPetOptions`, `...RequestOption`, `*ApiResult[Pet]`).
- Templates never read vendor extensions that came from the spec, and every generated file is a Mustache file. A value the generator computes is computed in Java and passed under a name without an `x-` prefix (`vendorExtensions.op.<name>`, the existing mechanism).
- `.github/workflows` is never edited from this repository.
- The shared test catalogue `src/spec/resources/test-catalogue.txt` holds one behaviour id per behaviour, and every language names a test from the id or has a documented exception in `test-catalogue-exceptions.txt`. `TestParitySpec` runs in strict mode (`ParityIdComparison.STRICT = true`, verified in `src/spec/java/.../parity/ParityIdComparison.java`).
- F879 (go has a per-group interface, with a compile-time assertion) is already settled and stays; this design extends its idea, it does not reopen it. Verified in `generators/AGENTS.md` and in `generated/go/pkg/pet_api.go` (`var _ PetApiInterface = (*PetApi)(nil)`).
- Tests: units mirror the source file; specs belong to one command; every fix is backed by a test that fails without it; no catch-all or feature-named test files (global rules). So no new test file is created: tests go into the existing client and api test templates.
- Documentation tree: every change that adds public API updates the README templates, `docs/languages/<lang>.md`, `docs/decisions.md` and the right `AGENTS.md` in the same pull request (root `AGENTS.md`).

## The shared behaviour

The promises, as catalogue lines in the format of `test-catalogue.txt` (`areaNNN | promise`, optional `| multi`). A new area `mocking` is proposed; the id regex `bhv([a-z]+)(\d{3})` accepts it (verified in `generators/AGENTS.md`, test layout section). The names below say "interface"; each language reads it as interface, protocol, trait or behaviour.

```
mocking001 | Every API group has an interface that lists every operation of the group and its with-http-info variant, and the generated group class implements it
mocking002 | The group interface lists exactly the public operations of the group class, no more and no fewer
mocking003 | A hand-written fake of a group is accepted wherever the group interface is accepted, and receives the operation call with the arguments the caller passed
mocking004 | A fake raises the SDK's typed error from an operation and the caller handles it exactly as it handles the error of the real client
mocking005 | An operation called through the interface type on the real client sends the same request and returns the same result as the call on the class
mocking006 | Calling an operation without the per-call options reaches the fake's full-signature method with the options absent, so a fake implements one form per operation
mocking007 | The top-level client interface exposes every group typed as its group interface, plus close, and the real client implements it
mocking008 | A fake client built from fake groups never opens a connection, and closing it does nothing and does not fail
mocking009 | The README has a section named "Testing your code" that names the group interface, the top-level interface and shows a fake, in the same words in every language
```

Applicability, so the exceptions file can be written without surprises:

- mocking006 is trivially true where one signature covers both forms (go, rust, dart, node, python, ruby, elixir, swift via a protocol extension, see the table). It is a real test in java, kotlin, csharp, php. Where it is trivially true the test still exists: it calls the operation without options through the interface and asserts the fake saw an absent options value.
- mocking007 and mocking008 have no meaning for go and elixir as an interface (neither can state fields, see the table). For go the same promise is met by the client struct with interface-typed fields; for elixir the client is a struct of group structs and the fake is the group behaviour. Each of the two gets a one-line entry in `test-catalogue-exceptions.txt` naming that limit, and go keeps mocking008 itself (a client built from fakes closes cleanly), which is the one place the shared client code changes (see the go row).
- mocking009 depends on the README tests. Only go has a `readme_test` in the goldens I listed (verified in `generated/go/test/readme_test.go`); the other eleven are not verified. The catalogue already shows `readme` as a partial group tracked in #118 (verified in `src/spec/resources/test-parity-allow.json`). The README promise is therefore tested where a readme test exists and exceptioned elsewhere until #118 closes.
- The #122 leak rule ("no public signature exposes a third-party type") is not a catalogue line here: it is the surface guard's job and will cover these names the day it lands. Until then the reviewer rule is: the interfaces use only the types of the class they mirror, which are SDK types and standard-library types (go `context.Context` and `io.Reader`, rust `std` futures, and so on).

## The shared generator changes

The shared generator needs little, because everything an interface lists is already computed for the class. Verified in `AbstractBetterCodegen.java`: `populateOperationDecorators` already puts `signatureArgs`, `signatureArgsNoServer`, `signatureArgsNoOptions`, `signatureArgsNoServerNoOptions` and `optionsArgOptional` on `vendorExtensions.op` (lines 3839 to 3864), and `postProcessOperationsWithModels` puts `clientPropertyName` on every API group (line 4963). `clientClassName` defaults to `Client` (line 538). The Go interface already renders from these (verified in `templates/go/api/api.mustache`, lines 100 to 109).

1. `AbstractBetterCodegen.populateOperationDecorators`: add one decorator list, `vendorExtensions.op.interfaceMembers`, an ordered list of `{name, withHttpInfo, args, isConvenience, delegatesTo}`. The canonical members (full options, full server argument) are abstract; the convenience members (the four stripped argument lists above) are marked `isConvenience` and carry the canonical member they delegate to. Why shared: java, kotlin, csharp, php and swift all have overloads or default arguments, and today the overload set is re-derived inside each `api.mustache` with conditionals (java: `optionsArgOptional` at lines 168, 475 and 527 of `templates/java/api/api.mustache`, verified). Six templates that each re-derive the set drift from the class and from each other, and mocking002 would catch the drift only after the fact. Go, node, python, ruby, dart, rust and elixir read only the canonical members and ignore the flag.
2. `AbstractBetterCodegen`: one name-collision guard for the new type names (`<Group>Api` plus the language's suffix or prefix, and the client interface name), applied where `toModelName` and the model-name collision logic live (lines 2525 to 2552). A schema called `PetApiInterface` or `ClientInterface` must not overwrite the new file. Not verified: whether a guard for the existing `<Group>Api` class name already exists; check before writing the new one so the two use one list.
3. Per-language `Better<Lang>Codegen.java` wiring (not shared, listed so nothing is forgotten): register the interface file. For languages with one file per class (java, kotlin, csharp, php, dart, swift) add an `apiTemplateFiles` entry with the suffix (java `Interface.java`, for example) and a `supportingFiles` entry for the client interface, named from `clientClassName`. For languages that keep the interface in the group file (go, node, python, rust, elixir, ruby `.rbs`) no new file is registered; the template changes only. Ruby already registers `api/api_rbs.mustache` and `infrastructure_rbs.mustache` (verified in `BetterRubyCodegen.java`, lines 87 to 89 and 362 to 363).
4. No change to `AbstractBetterCodegen.processOpts` or to the Docker formatters: every new file is code in a language that already has a formatter, linter and type check in its gate.
5. Documentation and rules, written in the same pull request: a new settled decision in `generators/AGENTS.md` ("Owner decisions of 2026-11-17" section; the id follows F879 and widens it), a row "Mock seam" in the idiom matrix, one paragraph in `docs/decisions.md`, the `go/AGENTS.md` mention of F879 updated, and every `generators/<lang>/AGENTS.md` that gets a new file. The root `AGENTS.md` sentence "No public API guard yet" stays true until #122 lands; the new names are listed there as the shape a reviewer holds every language to ("The public API shape" section).

## Naming rule

Same stem in every language: the group class name plus the language's word for the contract; the top-level name is the client class name (`clientClassName`, default `Client`) plus the same word. The class names do not change. The suffix is the language's own word (the root `AGENTS.md` allows `interface`, `protocol`, `trait`, `behaviour` as the only varying token), except where the language has a convention that prefixes (C#, which already uses `IAuthenticator`, verified in `csharp/src/PetstoreClient/Client.cs`).

## The tests

All tests go into the existing templates; no new test file is created. Two homes, by the mirror rule: the top-level and the group-generic tests go into the client test template of the language (they loop over `{{#apiInfo}}{{#apis}}` like the existing `bhvLifecycle001` test, verified in `templates/go/test/client_test.mustache` and `templates/java/test/ClientTest.mustache`, so no petstore word enters the template and `FixtureVocabularyLeakTest` stays green); the tests that call a real operation go into the existing `api/PetApiTest` family. The test names carry the id in the language casing, such as `bhvMocking003...` (java), `TestBhvMocking003_...` (go), `test_bhv_mocking_003_...` (python). A fix is proven by reverting it once.

The example for the README is the same three steps in every language: a function that takes the group interface, a fake that implements it, an assertion on what the fake saw.

## Risks and open questions

1. The interface grows when the spec grows. A new operation adds a method, and every hand-written fake that implements the whole interface stops compiling after the SDK is regenerated (java, kotlin, csharp, php, swift, dart, rust). The go interface already has this problem (F879). Recommended answer: accept it, say so in the README section ("a new operation in the API adds a method; embed or delegate to the generated type so only the operation you fake is written"), and give the recipe per language (go struct embedding, kotlin `by` delegation, java a base fake class or a `Proxy`, csharp `DispatchProxy`, swift a base struct). Do not make interface methods default-throwing: it hides a missing fake method until run time and removes the compile-time check that the class implements everything.
2. Rust has no zero-cost way to give an `async` trait that is both dyn-compatible and lint-clean. Recommended answer: `-> impl Future + Send` desugared trait, generic fakes, no `dyn` and no new dependency (`async-trait` would be a new runtime dependency, against the owner's standing preference for a small pure library only when it standardises behaviour cleanly). Cost: size L, the largest in the set, and the Rust gate runs only on CI. The alternative, boxed futures like `ApiClient`, doubles the generated code and gives a signature nobody would write by hand.
3. Widening a Go-only #131 line to twelve languages and changing the declared type of Go's client fields. Recommended answer: the owner confirms the widening (this document assumes yes), and the type change on `Client.Pet`, `Client.Problems`, `Client.Store` lands now because the SDK is pre-release and the public shape is being fixed (the root `AGENTS.md` goal), not later when it would be a break. Everything else in this design is additive.
4. Java and PHP need accessor methods (`getPet()`) next to the public field or property, so the client has two ways to reach a group. Recommended answer: accept it and document the field as the primary form and the accessor as the interface form; the alternative (no top-level interface in these two) leaves two languages without mocking007 and breaks "identical capabilities".
5. Swift: an associated type keeps `Client.pet` concrete but makes `ClientProtocol` usable only as a generic constraint or as `any ClientProtocol` (Swift 5.7 and later; `swiftLanguageModes: [.v5]` is verified, the existential use is not compiled). Recommended answer: the associated type, because the other choice (`any PetApiProtocol` as the declared type of `Client.pet`) changes the type of a public property for every user. Prove it with a compile in the Swift gate in stage 1.
6. Ruby: ship only the RBS interface, or also a runtime module that fakes can `include`. Recommended answer: RBS only. A runtime module is code with no behaviour that duck typing does not need, and the Steep `:test` target runs with core diagnostics off (KT-3), so a module would not be enforced anyway. Revisit if a Ruby user asks.
7. Elixir cannot substitute a group value, only a module (verified in `api/pet_api.ex`). Recommended answer: document the module indirection recipe and keep it out of the SDK; do not add Mox, and do not loosen the `PetApi` struct match to make values substitutable, because that would change a settled function head for every caller.
8. Name collision between a schema and a new type name (`PetApiInterface`, `ClientInterface`, `IClient`). Recommended answer: one guard in `AbstractBetterCodegen` (change 2 above) and one probe-spec schema for it, per the rule that every template shape is tested against a fixture that triggers it (`src/spec/resources/specs/probe/openapi.yaml`, verified to exist).
9. The surface guard #122 is not built yet, so these new public names are checked by hand until it lands. Recommended answer: land this work before or with #122's first snapshot, so the snapshot starts with the interfaces in it and the leak rule is checked on them from day one; list the twelve names in the shared "public API shape" paragraph now.
10. README alignment. The `### ` headings already differ between languages (verified by listing java, node, python and go READMEs: for example node has "Closing the client" and "Models", go has "Custom HTTP client" and "Models are immutable"). The root rule says sections are the same in all twelve. Recommended answer: add "Testing your code" after "Custom HTTP client" (python, go and java all have that heading; node and others not verified) in all twelve, and do not try to fix the older drift in this change.

## Order of work and size

Sizes: S is a template and doc edit with a golden diff; M is a new interface file or block, class changes, client changes and tests; L is M plus a real language limit that needs a design decision during the work.

| 0 | Owner confirms the widening and the five recommended answers (risks 1, 2, 3, 5, 6); write the decision into `generators/AGENTS.md` and `docs/decisions.md`; add the nine catalogue lines and the exceptions | all | S |
