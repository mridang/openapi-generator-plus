# Test alignment plan: the un-numbered extras

Analysis only. No template or golden was changed. Everything below is regenerated by the scripts in this directory (`scan.py`, `extract.py`, `cluster.py`, `analyze.py`, `multi.py`, `make_plan.py`; no network, no randomness) from the goldens at commit `b62e10ee2`.

## Headline numbers

- **3291 tests carry no catalogue id** (csharp 272, dart 228, elixir 226, go 271, java 243, kotlin 219, node 346, php 253, python 428, ruby 270, rust 247, swift 288). Their static scan counts match the parity check ("about 220 to 430 per language").
- Clustering across languages produced **828 candidate behaviours that exist in 2 or more languages**, covering 2155 tests (plus 144 same-language sibling tests attached to them). The other **992 extras are one-offs** (one language only).
- Reliability (hand-reviewed sample, see Method): high tier 448 groups, about 89% correct; medium 214 groups, about 79%; low 166 groups, about 33%. Expected number of genuinely shared behaviours: **about 623 of 828**. Recall is also imperfect (some real partners sit among the one-offs), so the true shared count is somewhat higher than the grouped count would suggest.
- **If every candidate group were promoted into the catalogue it would add 828 behaviours and 7781 missing tests** (sum over groups of the languages lacking it). Promoting only high+medium groups adds 662 behaviours and 6130 tests. The extras are mostly NOT shared across languages, so full alignment means writing roughly 6 to 8 thousand new tests.

### Effort estimate

Assumption (not measured): 10 to 15 minutes per added test, because each test is a template edit, a golden regeneration (all 12 goldens must be committed current) and a run of that language's suite, with CI at about 25 minutes per push. So scenario A is about 46 to 70 hours, B about 152 to 228, D about 1022 to 1532, E about 1297 to 1945 hours of focused work. The estimate excludes the work of deciding which candidate is real (review of the medium and low tiers) and fixing generator bugs the new tests will expose, which on this project has been the larger part.

## Recommendation

1. Do not promote every candidate. Two-language groups are 517 of 828 and cost 10 tests each; most are two sibling SDKs that happened to regress-test the same internal. Start with scenario A or B (high+medium, 4 or 5+ languages): 43 and 122 behaviours, so the owner gets the broadly shared ones without paying for coincidences.
2. Treat the low tier as a review queue, not a work list: about two thirds of it is wrong.
3. One-offs: see the next section. The only sound way to shrink the extras without writing thousands of tests is to decide per one-off whether it is language-specific (keep, and keep it excused) or noise (delete).

## Method

1. `scan.py` (the existing static scanner, rooted at this worktree) finds tests per language; the behaviour-id rule is unchanged (first token `bhv<letters><3 digits>` after lowercasing and stripping non a-z0-9). `extract.py` records for each id-less test its file, line, subject file (SUT, normalised from the test file name) and first assertion line; `extras.json`.
2. `cluster.py` normalises names (camelCase/snake/space split, filler words and bare numbers dropped, synonym fold such as throws/raises/rejects, suffix stemming), scores every cross-language pair as 0.65 idf-cosine of name tokens + 0.25 idf-cosine of string/number literals in the body + 0.10 same SUT, then merges greedily by descending score with average linkage >= 0.36 and at most one test per language per group. A second pass attaches a leftover test (score >= 0.40) to the group of its best neighbour as a same-language sibling when that group already has a test in its language; siblings are not counted as coverage.
3. `analyze.py` gives each group an area by voting its members' nearest NUMBERED tests (and a per-SUT prior), numbers it after the highest existing id in that area, and drafts the promise sentence from the most descriptive member name. **The promise sentences are drafts derived from names, not reviewed prose; a human must rewrite each before it enters `test-catalogue.txt`.** `area_margin` below about 0.1 (20 groups) means the area vote was close; check those.
4. I read test bodies for a seeded sample (`sample.py`, verdicts in `review.json`): 53 groups, high 15 Y + 2 partial of 18, medium 13 Y + 1 partial of 17, low 6 Y of 18. Confidence labels come from those rates. All other groups are UNREVIEWED beyond the score.

## The `| multi` ids (118 lines)

Static scan, so run-time case counts are not visible. Findings:

- **Parametrised cases of one behaviour (fine): the large majority.** 101 of the 118 ids have exactly one test function per language and in each language at least one of them shows a data-driven marker (each/with/Theory/parametrize/table loop). The marker regex is permissive (any `for` loop counts), so "data-driven" is an upper bound.
- **Per generated scheme wrapper (fine, same behaviour once per wrapper class):** authapikey007, authbasic001/002/003, authbearer001/006/010, authscheme001/002, authscheme002, lifecycle004 and lifecycle015 repeat per wrapper (csharp 2 to 11, dart 8, rust 13, swift 2 to 13, go 2). These are one behaviour over the 13 generated wrappers.
- **Genuinely different behaviours hiding under one id (should get their own ids):**
  - `lifecycle004` (promise: ApiKeyAuthenticator HEADER rejects CR/LF and non-ASCII). Eleven languages test exactly that. **Swift has 13 tests tagged lifecycle004 that assert "a missing credential fails at construction" per wrapper** (ClientTests.swift line 338 onward). That is a different behaviour, mislabelled: the swift CR/LF header test is either missing or untagged. Verify and retag.
  - `authscheme001` in rust: the function named `..._bhv_authscheme_001_bhv_authbasic_003_a_missing_credential_names_its_variable` carries two ids; only the first counts, so the authbasic003 claim is invisible to the parity check for that test.
  - `serializationparam060` in rust has two functions: `build_query_string_encodes_reserved_by_default` and `..._keeps_reserved_when_allowed`. The promise is "wraps only when allowReserved is true", so these are the two sides of one rule (acceptable), but only rust splits them.
  - `authapikey011` in csharp has two functions (ASCII-whitespace-only and form-feed-only); both are variants of the one promise (fine).
- **Probably unnecessary multi flag (one function everywhere, no data-driven marker found):** authoauthtwopassword006, errors035, retries011, serializationwire014. Each bundles two claims in its promise ("refresh ... and falls back", "308 https->http ... (no body replay)"), so the single test may assert two behaviours; read the bodies before splitting.
- Cannot verify statically: whether a `multi` id that is parametrised in language X runs the same number of cases in language Y. Only the test reports can show that.

## What I could not verify

- Run-time test counts (parametrised cases) are not visible to the static scan; `scan.py` reports Kotlin missing 22, Node 27, Dart 3, Elixir 1 ids and Swift 37 stale exceptions at this commit, so the scan and the real parity check disagree slightly (names built dynamically or ids split across lines). The extras counts could be off by a few in those languages.
- Group correctness beyond the sampled 54 groups; recall of the clustering (a spot check of 16 random one-offs found about 5 with a real partner that scored below the threshold or collided on language, so the one-off list is inflated and the shared list undercounted, by an amount I can only bound loosely at between 10% and a third).
- Whether a candidate is a real contract (every SDK should behave so) or a language quirk is a judgement the scores do not make; "generalise-candidate" is a heuristic flag only.
- The proposed ids are provisional: numbering follows group order and will shift if any group is rejected.
