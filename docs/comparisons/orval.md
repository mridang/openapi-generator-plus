# Comparison with Orval

This document compares the generated TypeScript (Node) SDK with the client Orval 8.48.0 generates from the same petstore fixture (`src/spec/resources/specs/petstore/openapi.yaml`). It was produced mechanically: every page of the English Orval documentation (the guides and the reference pages) was listed, every feature on every page was read in the Orval source (commit `6dbacb2`, 2026-11-17), run on the fixture with the installed CLI, and compared with the generated Node SDK. A feature that could not be run, or that failed on the fixture, says so in its row instead of being guessed. The generated output that backs each row was kept outside the repository and can be reproduced by re-running Orval with the option named in the row.

Orval is a TypeScript-only generator that targets application frameworks (React, Vue, Svelte, Solid and Angular query hooks, Zod and Valibot schemas, MSW and faker mocks, MCP servers). Our SDKs are framework-free clients that share one capability set across twelve languages, so most framework-specific output has no consumer here and is declined with that reason. The verdicts use the same vocabulary as the ogen comparison in #131: adopt (all languages), adopt-in-subset, recipe-only (document, add no API), defer (an owner decision is needed first), decline, and already-covered.

## What to adopt

- **Required and nullable query params send an empty value instead of being dropped (issue 3712)** (adopt, page `guides/angular`): A required parameter is silently dropped, which breaks the OpenAPI contract, so every SDK should send the key. Adoption needs the shared fixture to gain a required nullable query parameter first, plus a test that fails without the fix, per the test rules. No current test fails.
- **x-enumNames (aliases x-enumnames, x-enum-varnames): member names taken from a vendor extension** (adopt, page `guides/enums`): Additive: a spec without the keys generates the same names as today, and the API owner chooses the names instead of values such as NUMBER_1 or on-hold. Verified on the fixture plus the guide's examples (/tmp/orval-audit/out/guides_enums/input/fixture-plus-enum-metadata.yaml), because the unmodified fixture has no such keys: One/Two/Three/Four, Alpha/Beta (x-enumnames) and Gamma/Delta (x-enum-varnames) were all applied. Caveats: the implementation must reach all 12 generators' enum templates and I checked only the Node template; the first matching key wins (read from code, not run); the object-keyed form is in code but not on the page and was not run.
- **x-enumDescriptions (aliases x-enumdescriptions, x-enum-descriptions): per-member JSDoc** (adopt-in-subset, page `guides/enums`): Verified on the Node/TypeScript side only: Orval writes /** Alpha description */ above Alpha, as the guide shows. A per-member doc comment is native in TypeScript and in other languages that support member doc comments, so Node should be first in the subset. I did not check which of the other 11 languages can carry a per-member doc comment, so the subset is a recommendation, not a verified list. Member descriptions are lost in union output (see the union entry), so the feature only holds for const and enum output.

## Decisions that need the owner first

The deferred features fall into a few themes, and each theme is one decision, not many: shipping mock and fixture helpers, runtime validation of requests and responses against a schema library (this reopens the settled decision S3), a framework-free cursor iterator, typed per-Accept return variants for operations with several response types, a response reviver, and returning errors as values. The per-feature reasons are in the appendix.
